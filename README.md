# astrbot_plugin_vtuber_monitor

面向 Bilibili 虚拟主播的直播订阅与周表追踪插件，主要为vibe coding产物。当前 **V0.7.14** 新增 `/vt_4016` 凌晨四点问候，支持主播多个别名、置顶动态截图及周表图合并转发、周表识别、历史缓存、受控调播、修订差异及通知重试。已实测授权主页读取、截图、DeepSeek Flash 图片解析和工具调用；真实聊天消息路由与自动推送仍需在机器人中验收。

## 配置界面（0.7.11）

配置按“常用设置、通知内容、直播监听、周表与调播、Bilibili 登录、高级设置”分组。每项使用短标题，依赖关系和默认值放在提示中；周表/调播模型使用模型选择器，截图浏览器使用下拉菜单。常用自动开关和模型排在最前面。

升级时自动将旧配置值迁移到对应分组，开关、模型、间隔及手动登录凭据保持原值。配置文件现为分组结构，例如 `live.live_poll_interval`；文档中的参数名对应组内同名字段。顶层隐藏兼容项仅用于旧版迁移，不要再手动编辑；以分组内的值为准。扫码登录凭据仍保存在原数据库，不受影响。更新后重载插件并重新打开配置窗口。

## 特别关注自动启用（0.7.10）

`auto_special_live` 默认开启，添加 `special` 订阅后自动监听上下播，无需开启全体订阅的直播开关；普通关注仍由 `enable_live_polling` 控制。原来已开启全体监听的配置保留。

`auto_adjustment_with_schedule` 默认开启。特别关注主播有本周周表，且配置了 `multimodal_provider_id` 时，自动每 300 秒读取动态并处理调播，无需另外打开动态轮询或调播处理开关。手动解析或每日检查建立本周周表后，下一轮自动生效；仅有历史/下周周表时等待本周周表，不将修改应用到其他周。缺少周表或模型时不消耗调播任务重试次数。

自动调播与通知分开：是否发送调播结果仍由 `enable_adjustment_push` 控制。若要彻底关闭自动调播，关闭 `auto_adjustment_with_schedule`；若要停止所有直播监听，关闭 `auto_special_live` 和 `enable_live_polling`。配置修改后重载。

## 直播轮询退避与随机间隔（0.7.9）

正常轮询在每轮完成后等待 `live_poll_interval` 至 `live_poll_interval + live_poll_jitter` 秒，默认 120–180 秒；将 jitter 设为 0 可关闭随机等待。

遇到 HTTP 412/429 或接口 -352/-412/-509 时不进行秒级重试，立即停止本轮剩余主播查询。连续受限按 5、10、20、40、60 分钟冷却，成功请求后重置；遵守接口返回的更长 Retry-After 等待时间（秒数或 HTTP 日期）。冷却后还会叠加少量随机等待。同一客户端对同一 API 域名共享冷却，其他 UID 的查询也无法绕过。`/vt_status` 显示随机间隔范围和直播冷却剩余秒数。冷却状态保存在内存，重载会重置；不需要通过反复重载恢复请求。

## 开播通知（0.7.8）

开启直播轮询并订阅后，开播消息包含主播名称、UID、直播间标题、直播间链接和封面图片。优先使用主播设置的封面，缺失时使用接口提供的直播关键帧；两者都没有则发送文字。平台拒绝图片消息时尝试回退文字通知。下播消息仍为主播信息和链接。修改标题或封面本身不会触发重复开播通知。

## 周表的发现与更新

**周表发现与更新**由独立的定时扫描负责（`schedule_scan_times`，默认 `00:30 / 12:30 / 20:30`）：到点后逐个检查**特别关注**（以及手动解析过的普通关注）的**当前置顶动态和最近几条动态**，发现新周表图或改过的图就解析入库。不再锚定"当初导入的那条动态"，所以主播换一条新置顶、把周表发成新动态都能被发现；同一张图按内容指纹去重，稳态下不重复调用模型。启动时会补查最近一个已过的时间点一次，同一时间点不会重复扫描。留空时间列表即关闭定时扫描。

**特别关注会自动解析**：订阅特别关注后立即扫一次，拿到周表就建立基准并进入定时检查，不需要手动执行 `/vt_parse_schedule`。**普通关注默认只有手动解析过才继续被检查**（`/vt_parse_schedule` 成功后建立基准）；打开 `auto_parse_normal_schedule` 后普通关注也会自动解析。手动解析仍然可用，且首次解析为上周时，下一次不同版本指向本周；首次解析为本周时下个版本指向下周，之后从最近成功保存的周次继续顺延。

每轮扫描比对周表图片内容及正文日期标记，**同地址换图也能检测**（当前采用的那张图每次都会重新下载比对），原图按内容独立保存；已经判定过"不是周表"的图片会记住结论，后续轮次不再重复分类。普通说明文字变动不触发周次顺延。

“一周”指北京时间周一至周日。该周第二个及后续不同版本交给模型结合历史周表判断同周修订或下一周，不强制顺延。重试同一个版本不增加更新次数。模型无法确认、请求失败或日期冲突时保留原周表，下一次检查重试；`/vt_status` 显示待处理原因和动态链接。手动重新解析可确认日期并替换待处理基准。

每个时间点只能观察该时刻留下的版本，无法还原期间发生后又被覆盖的多次编辑——把时间列表排密一点可以缓解。模型解析需要已配置的 `multimodal_provider_id`；未改动的周表不调用模型。自动通知沿用已有推送开关及动态轮询投递机制。

## 当前功能

- `/bili_login`（别名 `/vt_login`）：AstrBot 管理员私聊扫码登录，空 SESSDATA 也可使用。
- `/vt_ping`：返回 `VTuber Monitor OK`。
- `/vt_sub <uid> [normal|special]`：查询主播信息后保存当前会话的订阅；填写主播 UID，不是直播间号。首次特别关注会查询动态建立静默基线，查询失败不会保存新订阅或覆盖原级别。
- `/vt_follow_level <uid> <normal|special>`：修改当前会话已有订阅的关注级别。
- `/vt_unsub <uid>`：仅取消当前会话的订阅。
- `/vt_list`：列出当前会话的订阅。
- `/vt_live <uid>`：查询实时直播状态，不修改监听状态、不触发通知。
- `/vt_push_test`：向当前会话发送一条主动测试消息；需人工确认平台实际收到。
- `/vt_status`：查看监听运行状态、轮询时间及本次运行的失败/发送计数。
- `/vt_latest <uid>`：查询最新动态正文与链接，不修改动态检查点。
- `/vt_pinned <UID或别名>`：仅返回完整动态截图和识别为周表的图片；优先复用识别缓存，未知配图用视觉模型分类，不修改周表日程。
- `/vt_parse_schedule <UID或别名> [本周|上周|下周|YYYY-MM-DD]`：管理员下载并解析候选周表；支持相对周次或指定周一日期，可强制重试之前失败的图片。
- `/vt_schedule <uid>`：查看本周已保存的日程；不会把上周存档当作本周展示。
- `/vt_schedule <UID或别名> [本周|上周|下周|YYYY-MM-DD]`：查询指定周的最新缓存版本并返回**7 列时间轴图片**，也支持这周、本星期、上星期、下星期；相对周次按北京时间换算，周一开始。不填时查询本周。
- `/vt_schedule_history <uid>`：列出已缓存周次及各周版本数量。
- `/vt_alias <UID或已有别名> <新别名>`：添加个人别名，保留已有别名；可重复执行添加多个。
- `/vt_alias_del <别名>` 或 `/vt_alias_del <UID> <别名>`：仅删除指定个人别名，不取消订阅。

## 主播别名与用户映射

成功订阅时保存“会话 UMO＋发命令用户 ID＋主播 UID”映射；别名也按会话和用户隔离。当前会话的订阅和推送仍为共享的会话订阅：群里取消订阅会取消该群对该主播的订阅，不是只取消个人推送。

例如已有小路的订阅时：

```text
/vt_alias 1512246445 小路
/vt_alias 小路 Komichi
/vt_latest 小路
/vt_schedule_history 小路
/vt_schedule 小路 2026-09-21
/vt_follow_level 小路 special
```

所有接受 UID 的主播命令均支持当前用户的别名，也支持已订阅主播的完整名称。UID 始终可用。旧订阅不需要重建，设置别名即可补充个人映射；不能推断旧订阅最初由谁创建，因此不会伪造历史用户 ID。

查询省略主播参数时，优先使用当前用户在该会话关联的订阅；没有个人映射时回退到该会话订阅。仅有一个目标才自动选择，有多个时提示可选名称。比如仅有一个订阅时直接 `/vt_schedule` 即可。新建订阅仍须提供 UID/已知别名。

别名支持 1–24 个中文、字母、数字、下划线和短横线，禁止纯数字和空格；英文不区分大小写，兼容全角输入。同一用户在同一会话内可以为同一主播添加多个别名，但同名不能指向不同主播。重复设置同一别名不会增加重复记录。旧版已有别名自动迁移保留。

`/vt_list` 每位主播只展示一行，例如 `小路 / Komichi（UID 1512246445）— special`；无别名时展示主播名称。多个别名不会导致省略目标时被误判为多个订阅。

`/vt_alias_del Komichi` 只删除 Komichi，仍可使用“小路”。也可 `/vt_alias_del 1512246445 Komichi` 精确指定。仅提供 UID 或主播名称时，只有一个别名才直接删除；有多个时提示选择，不会全部清空。修改别名可先添加新别名，再删除旧别名。

取消会话订阅会删除对应活跃用户映射，但保留别名，方便重新订阅或查询历史周表；要清理别名请使用 `/vt_alias_del`。

重复订阅不会创建重复记录。当前版本仅支持能查询到直播间信息的主播。接口风控、网络失败或字段异常会返回错误，不会保存失败的订阅。V0.3.1 支持可选 SESSDATA 和二维码登录，不自动刷新凭据。

## 二维码登录

1. 在 AstrBot 插件页安装本插件依赖并重载，确认 `/vt_status` 显示版本 **0.7.14**。
2. 使用已配置为 **AstrBot 管理员** 的账号私聊机器人，发送 `/bili_login`（群聊不支持）。
3. 用 Bilibili App 扫描机器人发来的二维码，在 App 中确认登录。
4. 收到“登录成功”后，发送 `/vt_latest 1512246445` 验证动态接口。

二维码约 3 分钟过期，同一时间只允许一个登录流程；扫码确认后凭据立即生效，持久化到 plugin_data 的 SQLite 登录凭据表，重载后自动读取。二维码图片会在完成、过期、失败或正常卸载时清理。凭据以明文存储在本地数据库，不回传聊天、不写插件源码，也不更改已有普通/特别订阅或自动打开轮询。

已保存的扫码凭据优先于手填 `bilibili_sessdata`。失效时重新扫码即可；本版没有自动刷新和服务端登出功能。若同时启用原版 `astrbot_plugin_bilibili`，使用 `/vt_login` 避免 `/bili_login` 同名冲突。

## 调播与修订（V0.5–V0.7）

新动态先命中关键词，再交给指定模型理解；普通聊天不注册修改工具。模型仅可请求改期、取消、加播、改标题；UID、来源动态和读取版本由插件绑定，工具不能传任意数据库补丁。Service 验证整批操作后一次提交，非法场次、日期、时间、重复加播或并发版本冲突都不保存部分修改。

自动调播限本周周表、本周发布的动态；“今天/明天”以动态的北京时间发布时间为基准。没有本周周表时不把历史周表当作本周，也不凭空创建整周计划。无法唯一定位场次或动态含糊时要求模型不调用工具；语义理解仍可能出错，可通过预演和修订记录检查。

```text
/vt_adjust_test 小路 今晚的歌回推迟到21:00
/vt_revisions 小路
/vt_retry_adjust 小路 123456789
```

`vt_adjust_test` 仅管理员可用，调用真实模型但只预演，不落库、不推送。`vt_revisions` 展示最近十次修改、来源和前后差异。`vt_retry_adjust` 仅管理员可用，修复配置或本周周表后将指定失败动态重新入队，下一轮处理；已成功动态不会再次修改。

周表替换会比较新增、删除、时间、标题和状态，优先按稳定场次 ID 对齐；没有 ID 匹配时仅采用唯一标题或唯一日期时间，歧义保留为增删。周表、历史版本、修订与待发通知同事务保存。同一来源图片/正文已导入后，即使模型再次输出略有不同，也不会撤销后续调播；图片或正文更新后才作为新输入导入。已成功解析的内容跨日复用缓存。

动态归档、检查点及待处理任务同事务保存。模型失败最多尝试三轮，按动态顺序处理；失败次数耗尽后保留记录并继续后续动态，`vt_status` 显示失败数量。重启恢复任务；关闭自动调播期间接收的新动态仍入队，开启后仅处理仍属于本周的内容。首次订阅基线和全部退出特别关注后重新建立的基线不会重放旧动态。

周表/调播通知仅向特别关注会话发送，默认关闭；需动态轮询投递。通知按会话记录投递结果，最多尝试五轮，成功的会话不重复补发；取消订阅、降为普通或关闭通知后丢弃待发项。崩溃发生在平台已收到消息但本地尚未确认之间时，恢复后仍可能重复发送，不能保证严格恰好一次。耗尽重试后不无限发送，可查询 `/vt_revisions` 查看变更。

## 凌晨四点问候 /vt_4016（V0.7.14）

`/vt_4016` 按当前北京时间（UTC+8）找出本地时间正好是 04:00–04:59 的国家和地区，随机挑一个交给模型造句，再按北京时间加问候前缀发送。命中范围覆盖各国时区，多时区国家和领地按城市或地名单独列表（如美国纽约、俄罗斯伊尔库茨克、关岛）。同一段话里不会重复最近 12 次用过的对象；模型不可用或调用失败时回退到固定句式。

```text
/vt_4016
小路泥中午好+
现在是马里凌晨四点半左右
```

前缀的"+"、问候语分界（05:00–10:59 早上好、11:00–12:59 中午好、13:00–17:59 下午好、18:00–20:59 晚上好、21:00–04:59 晚安）以及凌晨判断都以北京时间为准。模型在「常用设置 → 凌晨问候模型」选择，留空复用周表识别模型。时区数据用 `tzdata`，Windows 上必须装该依赖，否则查询会退化为安全网结果。

## 实际直播落位（V0.7.13）

开播和下播会先记进 `live_sessions`，再落到周表场次的“实际”区间。匹配规则是**同一天、周表时间前后一小时内的最近场次**：周表写 08:00，实际 07:00–09:00 开播就记到该场次；超出窗口则作为**突击直播**新增一条场次，保留观测到的开始、结束和直播标题，不再丢弃。

落位有两个入口：直播轮询每轮结束后处理当轮观测，**周表导入成功后立刻回填**。因此周表晚于直播发布（周一早播、周二才发周表）也能补记到对应场次；更正后的周表出现真正的场次时，此前的突击直播条目会自动并入该场次。没有本周周表时观测保持“待落位”，不会凭空创建整周计划。

周表里写成“直播（内容待定）”这类**占位标题**的场次，落位时会用实测到的直播间标题替换，所以查周表能看到当晚真正播了什么。周表原本写了真实节目名时不会被覆盖；实测标题为空时保留原占位；同一张图重新解析仍是占位时也保留已补全的标题，只有更正后的周表给出真实标题才以周表为准。

开始监控时已经开播、且接口未返回开播时间的观测记不到起点，标记为“未记录（起点未知）”并停止重复扫描。`/vt_status` 显示待落位/未记录/已记录数量，`/vt_schedule` 的图片底部显示本周实际直播统计。

## 周表解析与历史缓存

### 置顶动态合并转发

`/vt_pinned 小路` 在 OneBot/aiocqhttp（如 NapCat）上发送一条合并转发：第一条是实际 Bilibili 动态卡片的完整截图；之后只附上被识别为直播周表的图片，保持原顺序。不再单独附上立绘、周边等其他配图，也不追加原来的正文和链接消息。完整截图仍保留原动态内容。其他平台（包括 WebChat、QQ 官方接口）按相同顺序分条发送；OneBot 合并转发报错时也会提示并分条回退。

优先复用当前动态/图片/正文对应的有效识别结果；“是周表但缺少日期”同样可以返回图片。尚未识别的配图使用 `multimodal_provider_id` 做仅分类的视觉调用，结果单独缓存，不调用 ScheduleService、不写周表或触发调播。首次识别多图时可能较慢并消耗模型额度，重复请求复用缓存。未配置模型或分类失败时，不将未知配图当作周表发送；没有已确认周表图时只返回截图。

截图使用 Playwright 独立无头浏览器，读取当前插件登录 Cookie，不读取个人浏览器资料、不访问第三方截图服务、不调用模型。浏览器每次请求结束或取消后关闭，插件卸载会取消等待中的截图任务；使用临时浏览器上下文，不写个人浏览器用户目录，截图作为内存图片发送。隐藏页头悬浮栏以避免遮挡正文，但保留真实动态卡片内容。

安装插件新增的 `playwright` 依赖后，`screenshot_browser_channel=auto` 优先使用已安装的 Playwright Chromium，Windows 缺少时使用 Edge。本机 Edge 已实测可用；其他机器可在 AstrBot 使用的 Python 环境执行 `python -m playwright install chromium`。也可配置 `msedge`、`chrome` 或 `chromium`。[Playwright 浏览器安装说明](https://playwright.dev/python/docs/browsers)、[截图说明](https://playwright.dev/python/docs/screenshots)。

截图最长等待 75 秒、最大高度 30000 像素、最大 20 MiB；原图下载沿用 10 MiB 限制。原图过大或下载失败时尝试 CDN 压缩预览并标注；仍失败则在相应位置保留图片链接。截图失败时第一条明确说明失败，其余图片和末尾文字继续返回，不会把错误页面冒充动态截图。需要有效网页访问权限，不能保证绕过 Bilibili 风控。

带图片的置顶动态或命中关键词的动态进入候选流程。支持新版 Opus 标题/正文/图片和字符串时间戳。置顶可能在同一动态 ID 上长期编辑，因此每轮独立检查图片 URL 与正文指纹，不受新动态 ID 检查点过滤；内容未变化时复用成功结果，失败候选次日或手动强制扫描可重试。

图片只从 Bilibili HTTPS 图片 CDN 下载，单张最大 10 MiB，保存在 plugin_data/schedule_images。图片与来源动态 ID、URL、解析时间、周起始日等元信息一并保留。没有模型时仅保存原图；有模型时通过 AstrBot `llm_generate` 解析，不提供任何修改工具。

仅 DAY1–DAY7 或星期一至星期日的图片需要具体日期依据，不默认当成本周。正文月日范围只在距离当前日期 45 天内、唯一匹配周一到周日时作为日期锚点。日期不足时提示“周次不明确”，用户确认后可用 `/vt_parse_schedule 满区 本周`、`/vt_parse_schedule 满区 上周`、`/vt_parse_schedule 满区 下周`，也可填写周一日期 YYYY-MM-DD。相对周次以命令处理时的北京时间为准，周一开始；支持“这周”“本星期”“上星期”“下星期”，回复显示实际采用的日期。省略参数仍不会自动假设本周。允许过去一年至下周范围内的周次，指定日期与明确正文/模型日期冲突时拒绝保存。原图不是周表时显示“已跳过”，不与模型请求失败混为一谈。空周表、非法时间、重复 ID、超出周范围不会覆盖已有日程，待定时间保存为 null。

过去周表与当前周表分开存储：允许解析过去约一年至下周的周表，历史表按 UID/周次保留多个内容版本，相同内容不重复入库。旧周表只归档，不替换本周/未来的当前状态。查询已缓存历史不调用网络或模型；不自动回溯抓取全部历史动态，也不自动清理缓存。

已经实测并缓存：`/vt_schedule 1512246445 2026-09-21`，6 场直播，其中一场时间待定。数据来自该主播置顶动态第一张周表图，默认 `/vt_schedule 1512246445` 不会把这一历史周冒充本周。

### 周表图片

`/vt_schedule` 默认把缓存周表渲染成一张日历网格图片：顶部是类似 B 站空间页的横幅——空间头图铺底、头像压在左下角、右侧是**主播原名**与 UID／周次／场次／修订号；主体是一周七天，今天所在列高亮；每场只显示时间、标题、状态徽章，以及必要时的原定与实际信息；底部是实际直播统计（已记录／突击／待落位／未记录）与生成时间。图片不包含动态链接。

标题用主播原名（B 站昵称）而不是别名：别名是给命令用的，图上用原名更好认人。原名取自订阅时记录的昵称，之后每次直播轮询都会用接口返回的 `uname` 覆盖，所以主播改名会跟着更新；取不到时退化为 `UID <数字>`。

头像与空间头图**按 7 天 TTL 刷新**，不是每天重抓：启动时扫一次、之后每天 04:30（北京时间，带最多 10 分钟随机抖动）扫一次，只处理缺失或过期的条目，全都新鲜时连浏览器都不会打开。扫描时间刻意避开零点，那时周表任务正在调模型、下图片。7 天是按「换装、周年才换图」估的；想更及时可以调小 `PROFILE_TTL_DAYS`。新订阅的主播在第一次查看周表时即时抓取，不用等到下一次扫描。

两者的地址只存在于空间页的渲染结果里——公开接口 `x/space/wbi/acc/info` 即使带 WBI 签名也返回风控（-352），`x/web-interface/card` 只给头像——所以这里复用插件已有的无头浏览器打开空间页读取图片地址，再按 256×256（头像）与 1680×350（头图）的固定尺寸从 CDN 下载，避免把整页原图塞进 HTML（实测某个活动头图原图 952 KB，改尺寸后 46 KB）。头图定位按三种信号依次退化：类名含 `toutu` 的元素、头图 CDN 路径（`/bfs/space/` 与 `/bfs/activity-plat/`）、宽幅背景兜底——只认 `/bfs/space/` 会漏掉活动头图。抓取不发送任何 Cookie，只允许 B 站域名请求，图片保存在 `plugin_data/profiles/<UID>/`，地址未变化时不重复下载。单主播实测约 1.7 秒（等页面元素就绪而不是固定等待）。

记录里带 `version` 标记：提取逻辑升级后，旧记录会被判定为过期并自动重读一次，不需要手动删缓存。抓取失败会保留上一次的图并在记录里标记原因，且不会推进 TTL 起点，下一次扫描会继续重试。

抓取失败会保留上一次的图并在记录里标记原因，且**不会推进 TTL 起点**，下一次扫描会继续重试；同一天内失败过就不再重复尝试，避免插件重载时反复开浏览器。页面正常但主播没设自定义头图不算失败，只退回浅色底或纯文字标题行，不影响出图。`/vt_status` 会显示该任务的运行状态。

卡片按“列头已经写明的信息不重复”来精简。**排期**方面，没被调播的场次直接在时间上显示完整区间（如 `20:00–22:00`），不再重复打印“原定 09-21（周一）08:00–10:30”；调播后的场次出现在新的一天，卡片时间就是调播后的开始时间，因此只标注原定时间，不再重复写“调播至 …”。**实际直播**只显示起止时刻与时长，例如 `实际 21:04–次日 00:40 · 3小时36分`——日期不重复（跨日才标“次日”），接口/观测的来源标注也不显示；仍在直播时显示 `实际 21:02 起 · 直播中`。场次按**有效日期**落列；周表里没有对应场次的观测标为“突击直播”并注明“周表外记录”。

网格下方是本周的四项统计：**直播总时长**、**平均直播时长**、**迟到次数**、**平均迟到**。口径如下：

- **时长**按场次累计，中途重开的两段相加；仍在直播的场次算不出时长，不参与总时长与平均，但仍参与迟到判断。
- **迟到**以排期开始时刻为基准，超过 5 分钟才算（5 分钟以内属于正常开播准备，否则每场都会命中）。调播过的场次以**调播后的时间**为基准——既然已经公告改期，承诺就变了，拿原定时间算会得出“迟到 1 小时”这种没有意义的数字。
- 待定时间与突击直播没有承诺，不参与迟到统计；没有实际开播的场次（取消、待播）两项都不参与。
- 数据不足时显示 `—`：例如没有任何迟到就显示 `迟到次数 0 次` 但 `平均迟到 —`，一场都没播完则时长两项都是 `—`。

### 未兑现直播

排期到点后仍未开播的场次会标记为**未兑现**：红色卡片（红边框、红时间、红徽章），并在页脚统计里计入「未兑现 N 场」。判定条件与口径：

- **没被动态调播**：`status` 为 `scheduled` 且没有 `rescheduled_start_time`。被调播过的场次已经有新的承诺时间，按新时间重新计时；取消（`cancelled`）与时间待定（`start_time` 为 null）的场次不参与判定，突击直播不在周表内也不参与。
- **超过阈值**：到点后超过 `unfulfilled_after_hours`（默认 2 小时）仍未开播即标记。判定挂在已有的直播轮询里（默认 120 秒一轮），不需要额外任务。
- **当天可撤销、跨天定稿**：如果当天之内又开播了，这条会被迟到的直播**回填**——撤销未兑现标记、状态改为已结束、记录实际区间，并计入迟到（那会是个大数）。这同时避免了「场地标记未兑现 + 同一场直播另记一条突击直播」的双条目。过了当地日期就定稿，次日才补播的会另记突击条目。
- 未兑现是判定出来的状态，**重新解析同一张周表图不会被抹掉**（否则每次重新解析都要重标一次，还会产生假的状态变更通知）。
- 判定按场次自己所在的周取周表，因此周日 23:00 的场次到点两小时已经跨周时仍能被正确判定。
- **一次观测只挂在一个场次上**。周表写 19:00、实际 21:39 才开播时，因为超出匹配窗口会先落成突击条目；之后 19:00 被回填时，突击条目会把这条区间交出去（没有区间的突击条目随即消失），不会出现「一条已结束、一条还在直播中」的重复。

文字版（关闭 `schedule_image_enabled` 或渲染失败回退时）保留更完整的细节：日期、原定时间、`（接口）`/`（观测）`来源标注都会写明，因为纯文本没有列头可以省略。

一周拆成上下两行、每行四列（周一–周四／周五–周日）。这是为手机可读性做的取舍：手机上图片会缩放到屏幕宽度，字看起来多大只取决于**字号 ÷ 图片总宽度**，与像素密度无关；整周七列并排会把图片拉到 1420px 宽、字号占比只剩 1.06%，必须点开才能看清。当前版式把宽度收到 840px、列数降到 4，字号占比约 **2.02%**（接近两倍），并且把没被调播的场次那行冗余的“原定”省掉，为放大字号腾出空间。

渲染在本机完成：用 Playwright 无头浏览器打开一段自包含 HTML 后截图，样式内联、不引用外部资源、不访问第三方文转图服务、不发起任何网络请求。图片缓存在 `plugin_data/schedule_render`，最多保留 40 张并按时间清理；缓存键取自最终 HTML，所以周表内容、版式参数或样式任何一处变化都会自动重新出图。图片宽度 840px、二倍像素密度输出（成品 1680px 宽）。`tests/render_preview.py --compare` 可渲染候选版式与当前默认版式对比。

配置项 `schedule_image_enabled` 默认开启。关闭后 `/vt_schedule` 仍返回原来的文字版。开启时若渲染失败（未安装 `playwright`、浏览器缺失、渲染超时或版面过长），会自动回退为文字并在日志中记录原因，查询本身不会失败。浏览器选择沿用 `screenshot_browser_channel`，安装与限制同置顶动态截图一节。

## SESSDATA 与特别关注

在插件配置的 `bilibili_sessdata` 中填写 Bilibili Cookie 的 **SESSDATA 值本身**，不要填写 `SESSDATA=` 或完整 Cookie，不要通过聊天命令提交。该配置标记 `secret: true`；只通过 Bilibili 域名 Cookie 发送，不写入订阅数据库，不在状态回复中输出。`secret` 标记不代表配置文件加密。

未保存扫码凭据且该配置留空时尝试匿名访问，是否可用取决于接口和风控。失效时可重新扫码，或更新手填配置并重载；有效登录也不能保证绕过 Bilibili 风控。扫码保存 SESSDATA、bili_jct、DedeUserID 等接口实际返回的 Cookie，不支持自动刷新。

特别关注动态仅扫描接口第一页，按数字动态 ID 排序。首次关注静默建立基线，后续将新动态与检查点同事务归档，重复响应、重启和置顶旧动态不重复接收。空列表是有效基线，异常响应不推进检查点。多个会话特别关注同一主播共享检查点；全部退出特别关注后重新加入会重新建立基线。

只保存动态发布者自己的正文/图片 URL，不读取转发原文，避免把他人的排期当成主播本人排期。周表候选单独处理同 ID 编辑；普通动态不重放编辑内容，也不补抓历史分页，长时间停机可能漏掉已翻页的内容。动态归档目前不自动清理。

## 直播监听

按 UID 去重轮询，只在已知状态发生 `offline → live` 或 `live → offline` 时通知每个订阅会话。初次未知状态只建立基线；轮播视为未开播。状态及最近变化时间持久化，重复轮询和重启后同状态不会重发。所有会话取消后重新订阅会建立新基线。

单个主播查询失败、单个会话发送失败不会中断其他主播/会话。主动消息通过 AstrBot `context.send_message()` 发送，平台无关；每次发送最多等待 15 秒。停止或重载会取消并等待监听任务退出，再关闭 HTTP 客户端。

**上下播通知仍为尽力发送**：先保存状态，再发送消息，不补发失败的上下播通知；保存状态后进程中断可能漏通知。V0.7 的持久化重试队列用于周表和调播通知。轮询间隔内发生并结束的直播也可能无法捕获。

## 存储与配置

使用 AstrBot `StarTools.get_data_dir()` 定位 `data/plugin_data/astrbot_plugin_vtuber_monitor/monitor.sqlite3`。所有 SQLite 操作集中在 DataManager，在工作线程执行并及时关闭连接。主播资料与订阅同事务保存，以 `(uid, umo)` 为订阅唯一键。

配置 `request_timeout`（默认 10 秒）与 `max_retry`（默认重试 2 次）。网络错误、412/429/5xx、部分风控错误和响应格式错误采用有界指数退避；登录失效或其他不可重试错误直接报告。卸载插件时关闭 HTTP 客户端。

- `enable_live_polling`：默认 `false`，开启后监听全部订阅；特别关注默认由 `auto_special_live` 自动监听。
- `auto_special_live`：默认 `true`，特别关注的**采集开关**（不是通知开关）——决定是否轮询特别关注的上下播。关闭后不再记录实际直播，实际落位、未兑现判定、迟到与时长统计会一并停止；是否推送消息由「通知内容」里的开关单独控制。
- `live_poll_interval`：默认 120 秒，范围 10–86400；指一轮处理结束后的等待时间。
- `normal_live_start_push` / `normal_live_end_push`：默认都是 `true`，控制普通关注的上播／下播通知。
- `special_live_start_push` / `special_live_end_push`：默认上播 `true`、下播 `false`。特别关注的上下播通知独立于普通关注开关，默认只在开播时推送。
- `schedule_scan_times`：默认 `00:30`、`12:30`、`20:30`。每天在这些北京时间扫描周表：看**置顶动态 + 最近几条候选动态**，发现新图或改过的图就解析。留空即关闭定时扫描。
- `auto_parse_normal_schedule`：默认 `false`。关闭时普通关注只有**手动解析过**（有基准）才继续定时检查；开启后普通关注也会自动解析周表并进入定时检查。
- `dynamic_poll_interval`：默认 300 秒，范围 30–86400。
- `multimodal_provider_id`：周表识别、调播判断与凌晨问候共用的多模态模型提供商 ID，留空则只缓存周表图片、不解析不调播，凌晨问候改用固定句式。需要支持图片输入（调播判断还要求工具调用能力）。本机已配置为 `deepseek/deepseek-flash`，确认使用官方接口并实测识别成功。
- `schedule_keywords`：默认周表、本周、schedule、直播安排、本周安排。
- `adjustment_regex`：默认 `改到|改为|改成|延期|推迟|提前|顺延|取消|鸽|补播|加播|临时`。仅允许关键词的 `|` 分支，不支持复杂正则，避免阻塞轮询。
- `enable_schedule_push` / `enable_adjustment_push`：默认 `false`；分别控制周表更新与调播通知，需要动态轮询投递。
- `schedule_image_enabled`：默认 `true`，`/vt_schedule` 返回 7 列时间轴图片；关闭后返回文字版。渲染失败自动回退文字。
- `unfulfilled_after_hours`：默认 `2`，排期到点后超过该小时数仍未开播且没有被动态调播的场次，在周表中标记为未兑现。
- `screenshot_browser_channel`：默认 `auto`，置顶动态截图与周表图片共用的浏览器通道，可选 `chromium`、`msedge`、`chrome`。

特别关注的上下播通知不受普通关注开关影响，由 `special_live_start_push`／`special_live_end_push` 单独控制。两种轮询独立取消。

**「监听」和「通知」是两件事**：`auto_special_live` / `enable_live_polling` 决定要不要去采集（采集影响实际直播记录、落位、未兑现与统计），`notifications` 组里的开关只决定观测到之后要不要发消息；关掉通知不影响记录与统计，关掉采集则所有通知都不会触发。另外周表更新与调播通知走的是动态轮询这条独立链路，不受采集开关影响。

配置修改后重载插件。V0.1 数据库会自动补充 `last_live_change_at` 字段，保留原订阅和状态。

## 测试

在 AstrBot 项目根目录运行（使用 uv 的隔离环境，不修改 AstrBot 的依赖）：

```powershell
uv run --python 3.12 --with httpx --with pytest --with pytest-asyncio --with ruff --with 'qrcode[pil]' pytest -q data/plugins/astrbot_plugin_vtuber_monitor/tests
```

测试使用临时 SQLite 数据库、HTTP MockTransport 和 AstrBot 命令桩，不访问真实 Bilibili、不向 QQ 发消息。结果及后续验收见 [PROGRESS.md](PROGRESS.md)。

另可使用已安装 AstrBot 的 Python 执行 `tests/runtime_smoke.py`，验证真实框架初始化/退出、FunctionTool/ToolSet 构造、调播命令的多词正文参数解析，以及周表图片能否被真实图片组件引用。脚本使用临时目录，不启动后台轮询、不读取现有凭据、不发送消息。

`tests/render_preview.py [输出目录]` 用样例周表渲染一张预览图片，同时输出对应的 HTML，便于人工检查 7 列时间轴版式；不传目录时写入系统临时目录，同样在本机渲染，不联网。

`tests/render_preview.py [输出目录] --live <UID>` 会用真实主播抓取头像与空间头图再出图（访问 B 站空间页与图片 CDN，用临时数据库，不发送任何消息）；`--compare` 额外渲染被否决过的候选版式用于对比。

`tests/live_adjustment_check.py --run` 为手动实网测试：使用本机配置的模型凭据，在临时数据库验证明确改期与非调播否定句。它会产生模型调用费用，但不修改现有用户数据、不发送平台消息；没有配置可用模型时不要运行。此测试不被 pytest 自动收集。
